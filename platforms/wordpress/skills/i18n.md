# Internationalization — translatable strings

> Load this skill when: writing any user-facing string in PHP or JS.
> CDN: `https://cdn.wp-admincss.com/wordpress/skills/i18n.md`

WordPress runs in dozens of languages. Plugin strings should be translatable from day one — retrofitting later means searching every file and risking missed strings.

## The four steps

1. **Declare a text domain** in the plugin header.
2. **Load the text domain** on `plugins_loaded` / `init`.
3. **Wrap every user-facing string** in a translation function.
4. **Generate a `.pot` template** for translators (typically via WP-CLI).

---

## 1. Declare the text domain

In the plugin header (`my-plugin.php`):

```php
/**
 * Plugin Name: My Plugin
 * Text Domain: my-plugin
 * Domain Path: /languages
 */
```

The text domain **must match the plugin slug** (the folder name). For `my-plugin/my-plugin.php`, the domain is `my-plugin`.

---

## 2. Load the text domain

```php
add_action('plugins_loaded', function() {
    load_plugin_textdomain(
        'my-plugin',                                        // text domain
        false,                                              // deprecated
        dirname(plugin_basename(__FILE__)) . '/languages'   // path to .mo files
    );
});
```

If your plugin is hosted on WordPress.org, **you don't need this code** — WP.org loads translations automatically. But include it anyway for self-hosted and dev environments.

## 3. PHP translation functions

### Simple strings

```php
$label = __('Save Changes', 'my-plugin');           // returns the string
_e('Save Changes', 'my-plugin');                    // echoes the string
```

### Strings with HTML / attributes (escape + translate at once)

```php
echo esc_html__('Plugin Settings', 'my-plugin');
echo esc_attr__('Default value', 'my-plugin');
echo esc_html_e('Plugin Settings', 'my-plugin');    // escape + echo
echo esc_attr_e('Default value', 'my-plugin');
```

### Plurals

```php
$message = sprintf(
    _n('%d item updated.', '%d items updated.', $count, 'my-plugin'),
    $count
);
```

### Context for ambiguous words

When the same word means different things in different places, give translators context:

```php
$tab1 = _x('Post', 'noun (a published article)', 'my-plugin');
$tab2 = _x('Post', 'verb (to publish)', 'my-plugin');
```

### Translator comments

For tricky strings, add a comment that the `.pot` extractor picks up:

```php
/* translators: %s is a user's display name. */
$greeting = sprintf(__('Welcome back, %s.', 'my-plugin'), $display_name);
```

The comment must be immediately before the function call, with `translators:` as the first word.

### Function reference

| Function | What it does |
|---|---|
| `__($text, $domain)` | Translate, return |
| `_e($text, $domain)` | Translate, echo |
| `_x($text, $context, $domain)` | Translate with context, return |
| `_ex($text, $context, $domain)` | Translate with context, echo |
| `_n($single, $plural, $count, $domain)` | Translate + plural |
| `_nx($single, $plural, $count, $context, $domain)` | All of the above |
| `esc_html__()`, `esc_attr__()`, `esc_html_e()`, `esc_attr_e()` | Escape + translate variants |
| `esc_html_x()`, `esc_attr_x()` | Escape + context |

## 4. JavaScript translations

WordPress also supports translatable strings in JS via the `@wordpress/i18n` package.

### Setup

```php
// Server side: enqueue and declare translations
wp_enqueue_script('my-plugin', $url, ['wp-i18n'], '1.0.0', true);
wp_set_script_translations('my-plugin', 'my-plugin', plugin_dir_path(__FILE__) . 'languages');
```

The third arg is the path to a directory of `.json` translation files (produced from your `.mo` files via `wp i18n make-json`).

### Use in JS

```js
import { __, _x, _n, sprintf } from '@wordpress/i18n';

const label = __('Save Changes', 'my-plugin');
const help  = _x('Author', 'profile field label', 'my-plugin');

const msg = sprintf(
    _n('%d item updated.', '%d items updated.', count, 'my-plugin'),
    count
);
```

In a non-build environment (no bundler), use the global `wp.i18n`:

```js
const { __, sprintf } = wp.i18n;
const label = __('Save Changes', 'my-plugin');
```

## 5. Generating the `.pot` template

The `.pot` (Portable Object Template) file is the master list of all translatable strings. Generate it with WP-CLI:

```bash
wp i18n make-pot . languages/my-plugin.pot --domain=my-plugin
```

For JS translations:

```bash
wp i18n make-json languages/   # converts .mo files to .json for the JS runtime
```

Ship the `.pot` file with your plugin. Translators fork it into per-language `.po` files, then compile to `.mo` for runtime use.

## 6. Common patterns

### Never concatenate translatable strings

```php
// ❌ NEVER — translators can't reorder concatenation
echo __('Created on ', 'my-plugin') . $date . __(' by ', 'my-plugin') . $user;

// ✅ ALWAYS — use sprintf so translators can rearrange
/* translators: 1: date, 2: author name */
echo sprintf(
    __('Created on %1$s by %2$s.', 'my-plugin'),
    $date,
    $user
);
```

`%1$s`, `%2$s` etc. let translators reorder arguments in their language (some languages put author first, date last).

### Don't translate empty strings, variables, or class constants

```php
// ❌ Useless — the value is dynamic, can't translate
$label = __($user_input, 'my-plugin');

// ❌ Useless — empty
__('', 'my-plugin');

// ✅ Translate the static piece, interpolate the dynamic
$label = sprintf(__('Hello %s', 'my-plugin'), $user_name);
```

### Never use variables for the text domain

```php
// ❌ NEVER — string-extraction tools can't follow this
$domain = 'my-plugin';
__('Hello', $domain);

// ✅ ALWAYS — literal string
__('Hello', 'my-plugin');
```

This is the #1 mistake AI agents make. Translation tools statically extract strings; they can't follow variables.

### Use `esc_html__` / `esc_attr__` at the boundary

```php
// ❌ Vulnerable — translation files can contain HTML
echo '<h1>' . __('Welcome %s', 'my-plugin') . '</h1>';

// ✅ Safe
echo '<h1>' . esc_html(sprintf(__('Welcome %s', 'my-plugin'), $name)) . '</h1>';
```

Even though YOUR `.pot` strings are plain text, a malicious or careless translator can add HTML. Treat translations as untrusted output.

## 7. Right-to-left support

For RTL languages (Arabic, Hebrew, Persian, Urdu), WordPress handles most of the CSS flipping automatically via an `rtl-css` build step. If you ship custom CSS, also ship an `-rtl.css` companion that flips margins, paddings, floats.

Tools: [RTLCSS](https://rtlcss.com/) generates the RTL variant from your LTR CSS. WP automatically loads `style-rtl.css` when the site is in RTL mode.

For inline styles in PHP, use logical properties:

```css
/* ❌ Direction-specific */
.my-card { margin-left: 16px; }

/* ✅ Logical (works LTR + RTL) */
.my-card { margin-inline-start: 16px; }
```

## 8. Common AI mistakes

- **Missing text domain** on translation calls — `__('Hello')` instead of `__('Hello', 'my-plugin')`.
- **Variable text domain** — `__('Hello', $domain)` breaks string extraction.
- **Concatenated sentences** instead of `sprintf` with placeholders.
- **Hardcoded English in HTML** — alt text, button labels, placeholders.
- **`_e()` for HTML-context output** — should be `esc_html_e()` or `esc_attr_e()`.
- **Forgetting `wp_set_script_translations()`** when using `__()` in JS.
- **Translating empty strings or variables** — only literal strings can be translated.
- **Different text domains in different files** — must match plugin slug, used consistently.
