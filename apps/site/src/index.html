Why the SDK exists

Plugin code that ships review-ready — even when an agent wrote it.

Three things go wrong with WordPress plugin development today. Plugin SDK fixes each one by construction, not by adding rules to remember.

⚠

AI agents generate plausible-but-wrong code.

They emit register_rest_route without a permission_callback, echo variables without esc_html, concatenate SQL instead of preparing it. The code reads fine. Reviewers reject it.

↻

Every plugin re-implements the same plumbing.

Settings registration, nonce wiring, sanitisation tables, REST schema validation — each plugin solves them slightly differently. Each slightly differently broken.

⎘

Admin UI drifts from WordPress.

Hand-rolled admin pages don't match WP — different fonts, different spacing, different button shapes. They look like a foreign overlay because they are. The reviewer and the user both notice.

How it works

Two files. The runtime owns the wiring.

The manifest declares what your plugin needs. The bootstrap hands it to the runtime. Security checks, validation, sanitisation, and dbDelta happen by construction — you don't write any of them.

plugin-sdk.json Manifest 
{
  "platform": "wordpress",
  "name": "Acme Forms",
  "slug": "acme-forms",

  "settings": { "page": {
    "title": "Acme Forms",
    "capability": "manage_options",
    "sections": [{
      "id": "general", "title": "General",
      "fields": [{
        "id": "api_key",
        "label": "API Key",
        "type": "password",
        "required": true
      }]
    }]
  }},

  "rest": {
    "namespace": "acme-forms/v1",
    "routes": [{
      "path": "/submissions",
      "method": "POST",
      "capability": "manage_options",
      "schema": {
        "type": "object",
        "required": ["email"],
        "properties": { "email":
          { "type": "string",
            "format": "email" }}
      }
    }]
  }
}
acme-forms.php Bootstrap 
require_once __DIR__ . '/vendor/autoload.php';

use PluginSDK\WP\Plugin;
use Acme\Forms\REST\Submissions;

add_action('plugins_loaded', function () {
    Plugin::fromManifest(
        __DIR__ . '/plugin-sdk.json',
        __FILE__
    )
    ->withRestHandler(
        'Acme\Forms\REST\Submissions::create',
        [Submissions::class, 'create']
    )
    ->boot();
});

/* That's it. The runtime now:
 *   - renders the Settings → Acme Forms page,
 *     sanitising every field on save with
 *     capability + nonce enforced;
 *   - registers POST /acme-forms/v1/submissions,
 *     checks current_user_can('manage_options'),
 *     validates the JSON body, then calls
 *     Submissions::create($request);
 *   - if you add database.tables[] to the
 *     manifest, runs dbDelta on activate.
 *
 * Handler stays focused on business logic. */

→ Validates against the schema at cdn.wp-admincss.com/wordpress/plugin-sdk.schema.json — VSCode + JetBrains autocomplete via the $schema URL.

Scenarios

What you actually do, day to day.

Six recurring WordPress-plugin tasks. Each is either a one-line CLI invocation or a small edit to your plugin-sdk.json. No new patterns to learn beyond the JSON Schema.

+

Add a settings field

Append to settings.page.sections[].fields[]. The runtime picks it up on next page load — renders, sanitises, persists. No new PHP.

Add a REST endpoint

Drop a route into rest.routes[] with a JSON Schema. Runtime runs cap check + body validation before your handler ever sees the request.

{ "path": "/submissions", "method": "POST",
  "capability": "manage_options",
  "schema": { /* … */ } }

Add a custom table

Declare in database.tables[]. Bump the manifest's version to force a re-run; dbDelta computes the diff so old tables migrate cleanly.

    "type": "BIGINT UNSIGNED",
    "primary": true, "autoIncrement": true }] }

Security by default

Capability. Nonce. Sanitize. Escape.

When you use the manifest, the runtime applies all four for every settings save and every REST request — your handler never sees raw $_POST or unauthenticated traffic. The code below is what the runtime is doing under the hood; the same pattern lands in your src/ for anything that lives outside the manifest.

boilerplate/src/Admin/SettingsPage.php 
// 1. Capability check — server-side gate.
if (!current_user_can('manage_options')) {
    wp_die(esc_html__('No permission.', 'my-plugin'));
}

// 2. Nonce verification — defense against CSRF.
check_admin_referer('my_save_settings');

// 3. Sanitize each field. Never trust $_POST.
$sanitized = [
    'api_key' => sanitize_text_field($_POST['api_key'] ?? ''),
    'mode'    => in_array($_POST['mode'], ['production', 'sandbox'], true)
                  ? $_POST['mode'] : 'production',
];

// 4. Escape every output.
echo '<input value="' . esc_attr($sanitized['api_key']) . '">';
1
Capability check

Server-side gate before any read or write.

2
Nonce verification

check_admin_referer() defends against CSRF.

3
Sanitize input

sanitize_text_field, in_array, type coercion — never trust $_POST.

4
Escape output

esc_html / esc_attr / esc_url at the moment of render.

Database queries follow the same discipline — every $wpdb call uses prepare(). Full pattern walkthrough in platforms/wordpress/skills/security.md.
