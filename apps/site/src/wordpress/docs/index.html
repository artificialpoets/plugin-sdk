Documentation

Build, ship, and update WordPress plugins.

Plugin SDK is the agent-first SDK for WordPress plugin development. Declare what your plugin needs in a manifest, boot a runtime that wires every hook correctly, and ship through a pipeline that produces a wp.org-ready zip on every push to main.

Scaffold a new plugin

The fastest path. One command writes a working WordPress plugin with the manifest, runtime, build pipeline, CI workflows, and reference code already wired up.

npx @plugin-sdk/cli@next create "My Plugin"

Interactive prompts ask for slug, namespace, constant prefix, author, and distribution channel. For a non-interactive run:

npx @plugin-sdk/cli@next create my-plugin \
  --platform=wordpress \
  --channel=wp.org \
  --yes

The channel decides what ships with the scaffold (see Distribution channels). Default is wp.org — the safest baseline for Plugin Check.

Once scaffolded:

cd my-plugin
composer install
# Activate via wp-admin or wp-env, then visit Settings → My Plugin.

Every scaffolded plugin includes a working settings page, custom-table migration, REST endpoint, lifecycle hooks, PSR-4 autoload, i18n, scoped asset enqueue, the build pipeline, CI workflows, and the agent skills mirror on the CDN. Read the full file tour in Boilerplate walkthrough.

Add to an existing plugin

Already maintaining a WordPress plugin? Pull in the runtime via Composer and add a manifest at the plugin root.

composer require plugin-sdk/wp

Then create plugin-sdk.json next to your main plugin file and boot the runtime once:

<?php
require_once __DIR__ . '/vendor/autoload.php';

use PluginSDK\WP\Plugin;

add_action('plugins_loaded', function () {
    Plugin::fromManifest(__DIR__ . '/plugin-sdk.json', __FILE__)
        ->boot();
});

The runtime registers the menu, settings, REST routes, and database migrations declared in the manifest. Your existing handler classes keep doing what they were doing — the SDK doesn't take over the parts you've already built.

Just the CSS

If you don't want the runtime — say you're polishing an existing plugin's admin UI — drop in the CSS bundle and use real WordPress admin class names.

<link rel="stylesheet" href="https://cdn.wp-admincss.com/css/latest.css">

For production, pin to a version:

<link rel="stylesheet" href="https://cdn.wp-admincss.com/css/v0.1.0-rc.1/wp-admin.css">

Or via npm if you have a build pipeline:

npm install @plugin-sdk/wp-core-css @plugin-sdk/wp-tokens
# In your entry CSS or JS:
import '@plugin-sdk/wp-tokens';
import '@plugin-sdk/wp-core-css';

Browse the full component catalog for every primitive (forms, list tables, modals, postboxes, status badges) with copy buttons for HTML, AI prompts, React, and PHP. For this path you own every security check yourself — load the security skill when adding handlers.

plugin-sdk.json

The manifest is the single source of truth for your plugin's surface. It's validated against a JSON Schema at boot — anything malformed throws ConfigException with the full validation path. VS Code and JetBrains autocomplete via the $schema URL.

{
  "$schema": "https://cdn.wp-admincss.com/wordpress/plugin-sdk.schema.json",
  "platform": "wordpress",
  "name": "Acme Forms",
  "slug": "acme-forms",
  "textDomain": "acme-forms",
  "version": "0.1.0",
  "namespace": "Acme\\Forms",

  "settings":  { /* ... */ },
  "rest":      { /* ... */ },
  "database":  { /* ... */ }
}
Fail fast at boot

Validation runs once at plugins_loaded. A typo in settings.page.sections[0].fields[3].type throws on activate with the exact JSON Pointer to the offending node — not at the first user click three hours later.

Settings page

Declare the settings page structure; the runtime renders it inside options.php (so WP's nonce round-trip protects every save) and runs type-aware sanitisation per field.

"settings": {
  "page": {
    "title": "Acme Forms",
    "capability": "manage_options",
    "sections": [{
      "id": "general",
      "title": "General",
      "fields": [
        { "id": "api_key", "label": "API Key", "type": "password", "required": true },
        { "id": "env", "label": "Environment", "type": "select",
          "default": "production",
          "options": [
            { "value": "production", "label": "Production" },
            { "value": "staging",    "label": "Staging" }
          ]
        }
      ]
    }]
  }
}

Field types: text, password, email, url, number, checkbox, toggle, select, textarea. Each sanitises according to its type — email/url filter-validate, numbers clamp to min/max, selects whitelist against options, password preserves printables.

REST routes

Declare REST routes with a JSON Schema for the request body. Each request runs through current_user_can() + your schema before your handler executes. Invalid bodies return WP_Error('rest_invalid_body', ...) with the failing JSON Pointer — your handler never sees malformed data.

"rest": {
  "namespace": "acme-forms/v1",
  "routes": [{
    "path": "/submissions",
    "method": "POST",
    "capability": "manage_options",
    "handler": "Acme\\Forms\\REST\\Submissions::create",
    "schema": {
      "type": "object",
      "required": ["email"],
      "properties": {
        "email": { "type": "string", "format": "email" },
        "name":  { "type": "string", "maxLength": 200 }
      },
      "additionalProperties": false
    }
  }]
}

Wire the handler to the runtime at boot:

use Acme\Forms\REST\Submissions;

Plugin::fromManifest(__DIR__ . '/plugin-sdk.json', __FILE__)
    ->withRestHandler('Acme\\Forms\\REST\\Submissions::create', [Submissions::class, 'create'])
    ->boot();

The validator covers the Draft 2020-12 subset used in practice: type, required, properties, additionalProperties, enum, format=email|uri, pattern, minLength/maxLength, minimum/maximum, items.

Custom tables

Declare custom tables; the runtime registers an activation hook that runs dbDelta over each definition, gated on a version-stamped option so reactivations are no-ops.

"database": {
  "tables": [{
    "name": "submissions",
    "columns": [
      { "name": "id", "type": "BIGINT UNSIGNED", "primary": true, "autoIncrement": true },
      { "name": "email", "type": "VARCHAR(255)", "notNull": true },
      { "name": "created_at", "type": "DATETIME", "notNull": true, "default": "CURRENT_TIMESTAMP" }
    ],
    "indexes": [
      { "name": "email_idx", "columns": ["email"] }
    ]
  }]
}

The runtime emits dbDelta-compatible SQL with the two-space PRIMARY KEY (col) quirk baked in (it's the one dbDelta cares about). Table names are prefixed with the WP $wpdb->prefix automatically.

Bootstrap

The whole startup is one call.

<?php
require_once __DIR__ . '/vendor/autoload.php';

use PluginSDK\WP\Plugin;
use Acme\Forms\REST\Submissions;

add_action('plugins_loaded', function () {
    Plugin::fromManifest(__DIR__ . '/plugin-sdk.json', __FILE__)
        ->withRestHandler('Acme\\Forms\\REST\\Submissions::create', [Submissions::class, 'create'])
        ->boot();
});

What happens after ->boot():

  1. The manifest is loaded and validated against the JSON Schema. Failures throw ConfigException with the full validation path.
  2. If settings.page is declared, an admin menu page + WP Settings API registration are wired. Every field gets type-aware sanitisation.
  3. Each route in rest.routes[] is registered with a permission_callback that runs current_user_can() and an args/body validator that compiles to your schema.
  4. If database.tables[] is declared, an activation hook runs dbDelta over every table, gated on a version-stamped option so re-activation is a no-op.

Lifecycle hooks (register_activation_hook, register_deactivation_hook) stay at the top level of your main plugin file — they need to be registered before plugins_loaded fires.

Fluent API

The declarative manifest compiles to the same fluent calls. Use the fluent API directly when the manifest can't express what you need — they compose.

use PluginSDK\WP\Settings;
use PluginSDK\WP\Settings\Field;
use PluginSDK\WP\REST;
use PluginSDK\WP\Migration;
use PluginSDK\WP\Migration\Table;

(new Settings('acme-forms', 'Acme Forms'))
    ->capability('manage_options')
    ->section('general', 'General')
        ->field('api_key', 'API Key', Field::TYPE_PASSWORD, required: true)
    ->section('advanced', 'Advanced')
        ->field('endpoint', 'Endpoint', Field::TYPE_URL);

(new REST('acme-forms/v1'))
    ->route('/submissions', 'POST')
        ->capability('manage_options')
        ->schema([...])
        ->setHandler([Submissions::class, 'create']);

(new Migration('acme_forms_db_version', '0.1.0', 'acme_'))
    ->addTable(new Table('submissions', [
        ['name' => 'id', 'type' => 'BIGINT UNSIGNED', 'primary' => true, 'autoIncrement' => true],
        ['name' => 'email', 'type' => 'VARCHAR(255)', 'notNull' => true],
    ]));

plugin-sdk codegen

Generate a typed TypeScript REST client from your manifest. Useful when the React side talks to the routes declared in rest.routes[] and you want type-checked request bodies without re-declaring schemas.

npx @plugin-sdk/cli@next codegen \
  --manifest=./plugin-sdk.json \
  --out=./src/generated/plugin-sdk-client.ts

The output gives you a typed client to call from React:

import { createPluginSDKClient } from './src/generated/plugin-sdk-client';

const client = createPluginSDKClient({
  baseUrl: window.wpApiSettings.root,
  nonce:   window.wpApiSettings.nonce,
});

await client.submissions.create({ email: 'a@b.com' });

Re-run codegen whenever you add or change a route with a body schema.

Distribution channels

Picked at scaffold time via --channel. Decides which workflows and helper scripts ship with the plugin, and how update notifications reach users.

ChannelUpdates fromrelease.ymlreadme.txt + submission-prepPlugin Update Checker
wp.org (default) WordPress.org SVN — ✓ —
github GitHub releases (via PUC) ✓ — always-on
dual wp.org + GitHub (early-access opt-in) ✓ ✓ marker-gated

wp.org is the safest baseline for Plugin Check (no extra dependencies that might trip review). Pick github for plugins you don't intend to submit to wp.org (premium, internal company tooling, niche utilities). Pick dual when you want both — a stable channel via wp.org for the general user, plus a GitHub release channel for prerelease / early-access builds your power users opt into via the .use-github-updates marker file.

Build pipeline

Every scaffolded plugin ships with the tooling to produce a wp.org-clean distribution and self-check it before submission. Two entry points cover most workflows:

npm run build       # bash bin/build.sh   — produce build/<slug>/ + zips
npm run prep        # bash bin/submission-prep.sh — full pre-submission check
npm run slug-research # bash bin/slug-research.sh — wp.org slug availability

Under the hood:

  • bin/build.sh runs composer install --no-dev, rsyncs the source through .distignore, writes build/<slug>/ plus a versioned zip and a "latest" zip. Accepts a mode argument (wporg default, github for dual-channel builds that need the PUC marker).
  • phpcs.xml.dist declares the lint ruleset: WordPress Coding Standards + PHPCompatibilityWP, tuned to the boilerplate's prefix variants. composer run lint is the same check CI runs.
  • .github/workflows/ci.yml runs PHPCS + Plugin Check (against the built dist, not source) on every push and PR. See below for the release workflow.

wp.org submission

For wp.org and dual channels, npm run prep walks the same checks a wp.org volunteer reviewer will run, in order, exiting non-zero on any blocker:

  1. Working tree must be clean (no half-prepared dist).
  2. Version triple agrees — plugin header Version:, <PREFIX>_VERSION constant, readme.txt Stable tag.
  3. composer run check (phpsyntax + phpcs).
  4. composer test if a test suite is present (--skip-tests bypasses).
  5. bash bin/build.sh wporg — the dist that gets uploaded.
  6. Local Plugin Check (best-effort; skips cleanly if wp-cli isn't installed). CI's Plugin Check is the source of truth.

On success the script prints the SVN dance for first submission and the shorter trunk/tag dance for subsequent releases, with your slug + version substituted in.

bash bin/slug-research.sh <slug> is the companion: it validates the slug format, scans against ~20 trademark prefixes (wp-, woo-, yoast-, stripe-, etc.), and queries the wp.org plugin info API for availability. Slugs cannot be renamed after wp.org approval.

For the full operational walkthrough, agents should load skills/submission-prep.md.

GitHub release auto-bump

For github and dual channels, every push to main auto-cuts a new GitHub release. The bump level is decided by tokens in the head commit message:

git commit -m "Fix off-by-one in cron schedule"      # → patch bump (default)
git commit -m "Add CSV export endpoint [minor]"      # → minor bump
git commit -m "Drop PHP 7.4 support [major]"          # → major bump
git commit -m "Fix typo in readme [skip-release]"     # → no release

The workflow:

  1. Re-runs the quality gate (composer run phpsyntax + composer run lint) — defends against direct pushes to main that bypassed CI.
  2. Reads the current header version. If v<header> tag doesn't exist yet, ships verbatim. If it does, bumps per the commit-message token.
  3. Rewrites the version in three places — plugin header Version:, <PREFIX>_VERSION constant, readme.txt Stable tag — and commits the bump back to main with [skip-release] so it never recurses.
  4. Builds via bash bin/build.sh github (which writes the .use-github-updates marker for dual-channel installs).
  5. Runs Plugin Check on the built dist.
  6. Publishes a GitHub release with the versioned zip + an unversioned "latest" zip, --generate-notes, --latest.

For the full walkthrough including failure modes, agents should load skills/release-pipeline.md.

Plugin Update Checker

For github and dual channels, the scaffold includes a Plugin Update Checker (PUC) block in the main plugin file:

/* === PUC:BEGIN === */
if (
    file_exists(MYPLUGIN_DIR . '.use-github-updates')
    && class_exists(\YahnisElsts\PluginUpdateChecker\v5\PucFactory::class)
) {
    \YahnisElsts\PluginUpdateChecker\v5\PucFactory::buildUpdateChecker(
        'https://github.com/your-org/my-plugin/',  // ← edit me
        MYPLUGIN_FILE,
        'my-plugin'
    );
}
/* === PUC:END === */

The CLI rewrites this block per channel at scaffold time:

  • wp.org — the entire block is removed, the yahnis-elsts/plugin-update-checker dependency is dropped from composer.json. Updates ship via wp.org SVN.
  • github — the file_exists(...) check is replaced with true so PUC always runs. Updates ship via GitHub releases.
  • dual — block stays exactly as written; the .use-github-updates marker file (written by bin/build.sh github) decides whether PUC activates. wp.org users get wp.org updates; GitHub release users get GH updates.
Remember

The GitHub URL in the PUC block is a placeholder. Change it to your actual repo URL before the first GitHub release.

Real WordPress class names

Most "WordPress admin component libraries" invent their own class prefix — .wpac-button--primary, .acme-notice, that sort of thing. The output looks like WP, but doesn't behave like WP and doesn't fit cleanly alongside core admin pages.

Plugin SDK uses the actual WordPress admin class names: .button, .notice, .wp-list-table, .postbox, .form-table. The benefits compound:

  • Your plugin inherits the user's color scheme automatically. Same way WP core admin does.
  • WordPress-savvy developers can read your markup without learning a new namespace.
  • Your admin pages look indistinguishable from core WP pages. Less context-switching for the user.

Color schemes

WordPress ships nine admin color schemes: Default, Blue, Coffee, Ectoplasm, Midnight, Ocean, Sunrise, Light, Modern. Plugin SDK responds to all of them via the admin-color-* body class WP applies based on the user's profile.

<body class="admin-color-midnight">
  <!-- All tokens use Midnight scheme values -->
</body>

Inside a WordPress plugin you don't need to do anything — WP sets the body class for you. For previews or design demos, set it yourself; you can also apply it to any ancestor (not just <body>) to isolate the theming to one region.

Brand customization

Override tokens to skin your plugin while keeping the WP feel. Scope to a wrapper class so the rest of WP admin stays consistent:

.my-plugin-page {
  --wpadmin-primary: #7c3aed;
  --wpadmin-primary-dark: #6d28d9;
  --wpadmin-radius: 8px;
}
Pro tip

Scope your overrides to your plugin's wrapper element so the rest of WP admin keeps the user's chosen color scheme. WP power users get upset when plugins break their theming.

Building with AI agents

  • cdn.wp-admincss.com/wordpress/AGENTS.md — master entry point. Loaded first.

Key files to study:

  • plugin-sdk.json — the manifest. Edit this to add settings fields, REST routes, custom tables.
  • <slug>.php — the entire bootstrap is the Plugin::fromManifest(...)->boot() call inside plugins_loaded.
  • src/Admin/SettingsPage.php — canonical secure admin page. Capability check before reading state, nonce on the form, sanitize on input, escape on output. Copy verbatim for any hand-rolled settings page.
  • src/Database/EventRepository.php — every $wpdb call uses ->prepare(). Custom-table identifiers use the WP 6.2+ %i placeholder so table names get validated by $wpdb->prepare.
  • src/REST/SettingsController.php — REST endpoint with both permission_callback (capability check) and JSON Schema validation on arguments.
  • uninstall.php — runs on plugin uninstall. Drops the custom table, deletes options, scoped to be multisite-aware (loops sites if network-active).
  • bin/build.sh — same script local builds and CI builds use. Set SKIP_COMPOSER=1 to reuse an existing vendor/.

Stability contract

Plugin SDK follows semver. Pre-1.0 minor releases may introduce breaking changes; see STABILITY.md for the public-API contract.

Every public PHP symbol carries a @api docblock; internals carry @internal. The runtime classes table above lists exactly what's covered. A drift check fails the build if a new public symbol lacks a tag — adding a public class without thinking about its stability is impossible by construction.

The TypeScript packages (@plugin-sdk/wp-react, @plugin-sdk/cli) follow the same rule: anything exported from the root entry point is part of the public API; anything in internal/ isn't.

use PluginSDK\WP\Version;

Version::requireAtLeast('0.2.0'); // throws if older
echo Version::SDK; // "0.1.0-rc.1"

WordPress ships with nine admin color schemes: Default, Blue, Coffee, Ectoplasm, Midnight, Ocean, Sunrise, Light, Modern. Plugin SDK responds to all of them via the admin-color-* body class WP applies based on the user's profile.

<body class="admin-color-midnight">
  <!-- All tokens use Midnight scheme values -->
</body>

Inside a WordPress plugin you don't need to do anything — WP sets the body class for you. For previews or design demos, set it yourself; you can also apply it to any ancestor (not just <body>) to isolate the theming to one region.

Customize for your brand

Override tokens to skin your plugin while keeping the WP feel. Scope to a wrapper class so the rest of WP admin stays consistent:

.my-plugin-page {

Three brand previews on the landing page demonstrate the pattern — see the customize section on the home page.

Pro tip

Scope your overrides to your plugin's wrapper element so the rest of WP admin keeps the user's chosen color scheme. WP power users get upset when plugins break their theming.

Building with AI agents

The framework is designed to be agent-readable. The complete instruction surface lives at the repo root, hosted publicly so any agent can fetch it.

  • AGENTS.md — master entry point. Hosted at cdn.wp-admincss.com/AGENTS.md.
  • skills/ — focused skill files for the patterns AI commonly gets wrong (security, database, i18n, etc.).
  • boilerplate/ — a complete working plugin scaffold to clone for new plugins.

Point your coding agent at Plugin SDK using a prompt like this:

Read https://cdn.wp-admincss.com/AGENTS.md first.

For any state-changing action, load:
  https://cdn.wp-admincss.com/skills/security.md

For database work, load:
  https://cdn.wp-admincss.com/skills/database.md

For data modeling decisions:
  https://cdn.wp-admincss.com/skills/data-modeling.md

Most agents (Claude Code, Cursor, Cline, Aider) can fetch these URLs directly. If yours can't, paste the relevant content into the conversation.

Boilerplate walkthrough

The scaffold is a complete working plugin. Every file is a worked example of the patterns described in the skills directory — read them before you write similar code from scratch.

boilerplate/
├── plugin-sdk-starter.php  ← Plugin bootstrap (rename per project)
├── composer.json            ← PSR-4 autoloading
├── uninstall.php            ← Multisite-aware cleanup
├── src/
│   ├── Plugin.php           ← Orchestrator — wire up hooks here
│   ├── Lifecycle.php        ← Activation, deactivation hooks
│   ├── Admin/
│   │   ├── Menu.php         ← register_menu()
│   │   ├── Assets.php       ← Enqueue Plugin SDK from the CDN
│   │   └── SettingsPage.php ← Capability + nonce + sanitize/escape demo
│   ├── Database/
│   │   ├── Schema.php       ← dbDelta migrations
│   │   └── EventRepository.php  ← $wpdb with prepare()
│   └── REST/
│       └── SettingsController.php ← REST with permission_callback

Key files to study:

  • Admin/SettingsPage.php — the canonical secure admin page. Capability check before doing anything, nonce on the form, sanitize on input, escape on output. Copy this pattern verbatim for any settings page.
  • Database/EventRepository.php — every $wpdb call uses ->prepare(). The class methods are typed so callers can't accidentally pass user input as a column name.
  • REST/SettingsController.php — REST endpoint with both permission_callback (capability check) and JSON Schema validation on arguments.
  • uninstall.php — runs on plugin uninstall. Drops the custom table, deletes options, scoped to be multisite-aware (loops sites if network-active).
